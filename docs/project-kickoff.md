## 1. 출범 목표와 책임

첫 개발 목표는 **실제 iPad에서 한 페이지를 쓰고 지운 뒤, 앱을 다시 열어 이어 쓰는 경험**을 검증하는 것이다. 첫 제품 목표는 개인 필기와 마인드맵을 한 노트에서 안정적으로 쓰고, 다른 사람이 공개한 노트를 전체 복사해 공부할 수 있게 하는 것이다. 정보처리기사 파일럿에서 이 경험을 확인한 뒤 첫 배포를 판단한다.

팀 인원, 일정, 예산은 정해지면 반영한다. 아래는 역할별 책임이다. 초기에는 한 사람이 여러 역할을 맡을 수 있다.

| 책임 | 초기에 맡을 일 | 남길 결과물 |
|---|---|---|
| 제품·의사결정 | 범위, 정책 변경, 단계 진행 여부, 파일럿 해석 | 결정 기록과 단계 판정 |
| iPad 개발 | 실기기 입력, 로컬 저장, 편집기, 파일 가져오기, 백업 | 실행 가능한 빌드와 기기 검증 결과 |
| 서버·계정 개발 | 로그인, 공개본, 탐색, 복사 권한, 운영 기능 | 계정·권한 테스트와 운영 처리 경로 |
| 검증·파일럿 | 실패 재현, 회귀 테스트, 사용성 관찰 | 통과·실패·미실행이 구분된 기록 |
| 공유 운영 | 초기 콘텐츠 권한, 신고 처리, 작성자 안내, 배포 준비 | 콘텐츠 출처, 신고 절차, 개인정보·배포 검토 결과 |

## 2. 착수 준비와 우선순위

| 확인할 항목 | 필요한 시점 | 기록할 결과 |
|---|---|---|
| Mac·Xcode, Apple Pencil 호환 iPad, 기기 실행 권한 | 첫 필기 실험 전 | 실제 기기에서 빈 앱을 실행하고 기종·iPadOS를 기록한다. |
| 최소 iPadOS, 빌드·서명·협업 방식 | 개인 노트 개발 전 | 지원 범위와 CI에서 확인 가능한 항목을 남긴다. |
| 저장 구조와 자료 형식 | 자동 저장 및 백업 구현 전 | 이전 정상 저장본 보존, 버전 이전, 쓰기 실패 재현 경로를 확인한다. |
| DOCX 처리 | 외부 문서 가져오기 구현 전 | 대표 한글 파일의 문단, 표, 이미지와 페이지 표현을 확인한다. 지원 확장자와 데이터 처리 범위를 기록한다. |
| 인증·서버·첨부 자료 저장 | 공유 설계 초기에 | Google·Apple 시험 계정과 인증 설정, 공개 버전 권한 검증, 실패 재시도 방식을 정한다. |
| 권한 있는 공유 자료와 운영 담당 | 공유 파일럿 전 | 공개할 자료와 담당자, 신고 대응 경로를 마련한다. |
| 백업, 계정 삭제, UGC와 개인정보 | 첫 공개 배포 전 | 적용되는 정책과 사용자가 실제로 쓸 수 있는 복구 절차를 검증한다. |

필기와 저장을 먼저 개발한다. DOCX와 인증처럼 이후 일정에 영향을 줄 선택은 준비 작업으로 조사할 수 있다. Xcode나 실기기가 준비되지 않았다면 해당 기기 검증 결과를 미실행으로 기록한다. 문서·서버 계약·데이터 검증은 계속 진행할 수 있다.

## 3. 개발 단계와 전환 조건

V0는 M0~M2, V1은 M3~M6이다. M5는 공유 파일럿이고, 첫 공개 배포는 M6의 검증을 통과해야 한다. 아래 단계는 [로드맵의 P0 범위](development-roadmap.md#3-p0--확정된-v0와-v1-범위)와 연결된다.

| 단계 | 범위와 요구사항 | 다음 단계로 넘어가는 조건 |
|---|---|---|
| M0 · 준비 | iPad 빌드·서명, 실기기 장비 확인 | 빈 앱을 실제 iPad에서 실행한다. 담당 역할과 첫 실험 범위를 정한다. |
| M1 · 입력 실험 | INK-01의 펜·지우개·손가락 모드·이동·확대 | 손바닥을 올린 Pencil 필기와 두 손가락 이동에서 의도하지 않은 획이 없다. 실기기에서 V-05의 입력을 확인한다. |
| M2 · 한 페이지 저장 | INK-02, 취소·다시 실행, 자동 저장·실패 복구 | 저장 완료 후 강제 종료·재실행에서 쓰고 지운 결과가 복원된다. 쓰기 실패 후 이전 저장본과 편집을 보존한다. V-06의 단일 페이지 범위와 V-07을 확인한다. |
| M3 · 개인 노트 | NAV-01, NOTE-01, DATA-01의 기기 동작, INK-01 전체, DOC-01 | 여러 노트의 페이지와 변경 내용을 섞지 않는다. PDF·지원 워드의 원래 파일을 옮긴 뒤에도 오프라인에서 필기 탭을 연다. V-04, V-06, V-08의 해당 범위를 확인한다. |
| M4 · 마인드맵 | MAP-01과 두 탭의 복원 | 필기와 마인드맵 편집이 재실행 후에도 유지된다. V-09를 확인하고 V-04의 마인드맵 시작과 V-08의 가져온 노트에서 두 탭이 열리는지 검증한다. |
| M5 · 공유 파일럿 | AUTH-01, DATA-01의 계정 경계, FIND-01, FIND-02, PUB-01, PUB-02, COPY-01, LINE-01, OPS-01 | 두 계정 이상으로 공개→발견→즐겨찾기→복사→편집→재공개를 검증한다. 계보와 운영 테스트에는 필요한 계정을 추가한다. V-01~V-03, V-10~V-16, V-19를 확인하고 [파일럿](#4-정보처리기사-파일럿)을 진행한다. |
| M6 · 첫 공개 배포 준비 | BACK-01, 인증과 운영·배포 요건, 누적 회귀 검증 | V-17~V-18과 모든 필수 인수 시나리오의 최종 결과를 남긴다. 복구, 권한, 운영 대응과 배포 심사 항목을 확인하고 진행 여부를 기록한다. |

M1~M4의 내부 빌드는 현재 단계 범위를 대상으로 검증한다. **운영 기본값 제안**으로, M5 참가자가 주력 공부 자료를 장기간 iPad에 보관한다면 전체 백업·복원을 파일럿보다 먼저 검증한다. 첫 공개 배포 전에는 백업·복원과 누적 회귀 검증을 완료한다.

## 4. 정보처리기사 파일럿

### 준비

- 공유 권한이 있는 정보처리기사 공개 노트를 소량 준비한다. 필기 중심 노트와 마인드맵을 담은 노트를 포함하고, 참가자가 공부하는 범위와 자료가 맞는지 확인한다.
- 실제 공부에 써볼 수험생과 자기 노트를 공개할 작성자를 섭외한다. 수·기간·모집 경로와 담당자를 운영 전에 정한다.
- 내부 검증에는 별도 시험 자료를 쓴다. 열람 전용, 복사 허용, 원본과 수정본 사례가 있어야 한다.
- 참여자에게 공개와 복사 권한, 기기 내 보관과 백업을 안내한다. 개인 필기 원문과 백업 파일을 수집할 필요 없이 관찰할 수 있는 방법을 우선한다.

### 관찰과 판정

| 단계 | 관찰 방법 | 신호가 약할 때 먼저 확인할 것 |
|---|---|---|
| 발견 | 주제로 검색하고, 새로 발견한 내용을 본인 말로 설명한다. | 자료가 충분했는지, 제목·태그·소개로 찾을 수 있었는지 |
| 검토 | 공개 노트의 두 탭을 열고, 즐겨찾기나 복사 중 목적에 맞는 경로를 찾는다. | 권한 표시와 즐겨찾기·복사의 의미를 이해했는지 |
| 활용 | 사본에서 손글씨, 메모, 마인드맵 중 한 가지 이상을 바꾼다. | 복사 후 바로 편집할 수 있었는지, 입력이 편했는지 |
| 복습 | 다음 공부 시점에 사본을 다시 열고 자신이 쓴 내용을 찾는다. | 재열람 기회가 있었는지, 저장·홈·검색 경로에 문제가 있었는지 |
| 공개 | 노트를 올리고 공개본 업데이트와 권한 변경의 결과를 설명한다. | 공개 범위, 계정 명의, 출처, 복사 조건을 확인하기 쉬웠는지 |

**운영 기본값 제안**으로 각 단계의 진입 인원과 완료 인원을 함께 기록한다. 복사 횟수와 수정·재열람한 인원을 구분한다. 수험생 관찰과 후속 확인부터 사용하고, 자동 수집이 필요하면 수집 이벤트·보관 기간·동의를 검토한다.

필수 기능과 권한 테스트를 통과한 후 파일럿 학습을 바탕으로 배포를 판단한다. 참가 규모와 정량 목표는 담당자가 파일럿 시작 전에 기록한다. 결과가 애매하면 자료, 발견, 권한 이해, 편집, 복습 기회 중 어디에서 끊겼는지 파악해 다음 검증을 잡는다. 반복되는 문제가 후속 기능 후보와 이어지면 [로드맵](development-roadmap.md#5-우선순위를-다시-정하는-방법)의 기능 ID와 함께 관찰을 남긴다.

## 5. 공개 배포 준비

- **데이터 신뢰** · 실기기 입력과 재실행, 여러 페이지의 격리, 백업·복원, 오프라인 접근, 디스크 오류 재현 결과를 확인한다.
- **권한** · 양쪽 로그인, 로그아웃과 계정 교체, 작성자 지표, 즐겨찾기, 복사 권한 변경, 외부 파일의 공개 제한, 운영 계정 권한을 확인한다.
- **신고 운영** · 신고 접수와 버전 확인, 개별 공개본 내림, 저작권 파생본 안내, 복구 검토 담당과 문의 경로를 확인한다.
- **배포 심사** · 계정 삭제, 사용자 생성 콘텐츠 대응, 차단·문의 경로, 개인정보 고지, 로그인 제공과 심사 접근 방법을 점검한다. 검토 결과 사용자 기능 변경이 필요하면 기획서와 구현 명세서를 함께 갱신한다. [App Store 심사 지침](https://developer.apple.com/app-store/review/guidelines/)
- **배포 기록** · 실행한 빌드, 기기와 iPadOS, 테스트 결과, 미해결 결함, 검토 담당자와 날짜, 진행 여부를 기록한다.

개인 데이터 유실, 권한 우회, 비공개 데이터 노출, 출처 유실, 전체 복원에서 기존 자료 덮어쓰기는 **배포 중단 사유**다. 공유 범위에 맞는 운영 담당과 신고 처리 경로도 필요하다. 배포 후 문제가 발견되면 운영 기능으로 관련 공개본의 접근을 우선 줄이고, 개인 데이터에 영향이 있는 변경은 복구 가능성을 확인한 뒤 진행한다.

| 두 로그인과 계정 삭제 | 운영·심사에 필요한 정책이 지연될 수 있음 | M5 전에 인증 설계를 점검하고 배포 전 계정 삭제와 기존 공개 출처의 표시 규칙을 확정한다. |

| 출처와 저작권 운영 | 문제가 있는 파생본이 남거나 잘못된 대상을 내릴 수 있음 | 버전 기준 조치와 파생 단계 안내를 검증하고 심사 전 운영·이의 제기 기준을 정한다. |
| 공개 자료 부족 | 탐색·복사 수요를 해석하기 어려움 | 권한 있는 자료를 준비해 자료 적합성과 기능 사용을 따로 확인한다. |
| 복사를 학습으로 과해석 | 우선순위를 잘못 정함 | 복사 완료와 편집·재열람을 함께 관찰한다. |
| 기기 내 노트 분실 | 새 iPad에서 계정 로그인만으로 개인 편집을 되살릴 수 없음 | 배포 전 전체 수동 백업·복원을 다른 iPad에서 검증한다. |

## 7. 변경 관리와 첫 작업 묶음

제품 결정이 바뀌면 요구사항 ID, 로드맵 기능 ID, 변경 이유, 해당 단계와 검증 항목을 기록한다. 적용되는 문서를 함께 고치고 개정 이력을 갱신한다. 최초 통합 명세는 당시 합의를 확인하는 기록으로 보존한다. 기준 문서의 역할과 변경 절차는 [문서 버전 관리 규칙](README.md#문서-버전-관리)을 따른다.

1. Mac·Xcode 실행과 iPad 설치를 확인하고 기기 정보를 기록한다.
2. 한 화면에서 PencilKit 기반 펜·지우개와 두 입력 모드를 검증한다. 문제가 있으면 동작과 기기 조건을 기록한다.
3. 검증한 입력 화면에 한 페이지 저장, 실행 취소·다시 실행, 재시작 복원을 추가한다.

첫 세 작업의 결과는 실행 가능한 빌드, 실기기 입력 검증 기록, 저장·복원 확인 결과로 남긴다. 여러 페이지와 공개 기능의 상세 작업은 이 결과를 반영해 분해한다.
